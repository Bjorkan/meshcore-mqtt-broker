# Architecture

The supported deployment is one Docker Compose broker container, one long-lived Bun process, and one Aedes broker. The broker is stateless: MQTT sessions, retained packets, offline queues, QoS state, wills, observer state, abuse observations, and the MeshCore.io upload queue all live in process memory and reset on restart. There is no database. Healthchecks and CLI commands may use short-lived auxiliary processes. Do not add cloud state dependencies, coordination services, broker replicas, election, leases, distributed workers, Docker Swarm mode, or horizontal-scaling abstractions.

`src/server.ts` binds one plain HTTP server for MQTT-over-WebSocket upgrades and passes streams to Aedes. `GET /status` reports `{ status: "ok", storage: "stateless", instanceId, uptimeMs, observers, target, meshcoreIo }` (Docker HEALTHCHECK probes exactly this path, no credentials); all other ordinary HTTP paths remain 404. One broker identity is generated per process and shared by `/status`, logs, the target `clientId`, and `$SYS` quarantine topics; it rotates on restart by design (single-broker, no coordination). The listener authorizes the topic's uppercase three-letter IATA ingress code and serves no dashboard, REST API, OpenAPI, MCP, or frontend assets.

Startup failures during integration startup, listener binding, or post-bind initialization trigger bounded cleanup of WebSocket/HTTP listeners, Aedes, timers, and integrations before the original error is rethrown. A cleanup failure is logged without skipping the remaining cleanup steps.

Accepted observer publishes are authorized and distributed through Aedes. Exact `neighbors` messages are always retained locally and when forwarded to the target, including opted-in `test` ingress, regardless of the sender's retain flag; other client messages are nonretained. Expiry tracking is process-local. Local neighbor storage writes and expiry clears are serialized at the Aedes in-memory storage boundary: at 10,000 topics, the least recently refreshed value is removed before a new topic is stored. A failed capacity clear preserves the old value and timer and fails the incoming storage operation; failed expiry clears are retried after one minute. Local cleanup removes the retained storage value and broadcasts an empty message to current subscribers without re-storing it; retained lookups for future subscribers return nothing. Target retained writes and clears are serialized across topics so capacity checks cannot race. At capacity, the least recently successfully refreshed tracked value is cleared before admitting a new topic; failed clears preserve the old tracking entry and drop the incoming forward. A new topic reserves its expiry entry before writing so a failed or timed-out write does not lose its cleanup obligation. Remote retained clearing additionally requires target connectivity, and its deadlines are lost on restart. Normalized ingress fields use `iata`; MeshCore logical regions remain neighbor `scope` values and are never conflated with IATA. The broker routes neighbor scopes as supplied by observers; it has no snapshot projection or geographic scope registry. Target forwarding and MeshCore.io upload remain local in-memory process features.

Every connection or publish denial carries a stable machine-readable observer error code (`OBSERVER_ERROR_CODES` in `src/server.ts`, e.g. `AUTH_WRONG_AUDIENCE`, `PUBLISH_UNKNOWN_IATA`) plus a human-readable message. Auth denials surface as MQTT 3.1.1 CONNACK returnCode 5 with `[CODE] detail` in the error. Publish denials surface as the authorizePublish error and are additionally pushed as JSON (`{ code, message, topic?, iata?, at }`) to the observer's own `meshcore/<IATA>/<OWN_KEY>/error` topic on the same connection before any close, which is the only channel a QoS 0 observer is guaranteed to see. Observers should subscribe to their own `/error` topic at connect; the broker never accepts publishes to it. IP blocking is handled by CrowdSec/Traefik in front of the broker; abuse detection is observe-only logging.

The broker always runs alone. Observer ownership is a single in-process map: a newer authenticated connection for the same public key replaces the older one (the old connection is closed), and publishes from a stale connection are denied with `PUBLISH_STALE_CONNECTION`. Subscriber connection limits are counted in process memory.
